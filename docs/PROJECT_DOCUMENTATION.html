1. Executive Summary

1.1 What the system does

This project is a complete, production-shaped web platform that takes a video — CCTV footage, a phone recording, an incident clip — and answers three questions about it: was anything dangerous happening, exactly when, and what was it. It then lets the operator interrogate that answer in plain English.

A user signs up (with email OTP verification), uploads a video, and picks a detection strategy. The upload returns in about a second with a job identifier; analysis itself runs in a separate worker process. Within roughly one second of that, preview frames begin appearing in the browser, streamed live over Server-Sent Events, while the vision model is still loading. As the analysis proceeds, each detected incident arrives as its own event carrying a cut video clip, a bounding-boxed version of that clip, a still frame, a timestamp range, a confidence score and a plain-language explanation. When the run completes, the user can open a chat window attached to that specific scan and ask questions that are answered from the stored evidence — with citations back to the exact segments and frames used.

The central engineering claim No single model solves this problem. Detecting a gun in a frame, recognising that two people are fighting, and understanding that someone is being harassed are three different machine-learning problems with different input representations, different training data and different failure modes. The system's design is a direct consequence of that fact: it selects, cascades and combines specialised models rather than pretending one architecture covers the whole domain. Section 5 is the full argument.

2. Problem Statement & Objectives

2.1 Threat categories in scope

The platform was scoped around six target detections drawn from realistic security-monitoring needs: fighting, snatching and robbery, shooting or killing, harassment and assault, bombs and explosions, and visible weapons (gun, knife, grenade). These are normalized in the database into five categories with an assigned severity that drives colour and ordering in the user interface.

Table 2.1 — Incident categories as seeded in services/reference_data.py
CodeDisplay nameSeverityTypical source

harassmentHarassment4 — highGemini only (see §5.7)
accidentAccident3 — mediumUCF-Crime RoadAccidents, Gemini
otherOther Hazard2 — lowFire, arson, vandalism, arrest

2.2 Why this is three problems, not one

The single most consequential design decision in the project was recognising early that the target list splits along a technical fault line that has nothing to do with how a human would group the categories.

Table 2.2 — The three detection problems and their required model class
Problem classQuestion being asked Required input representationTargets covered
Object presence "Is a dangerous thing visible in this image?" A single still frame. Spatial reasoning only. Gun, knife, grenade, explosive, bomb
Action recognition "What are these people doing over the last few seconds?" An ordered stack of 16 frames. Motion and temporal reasoning. Fighting, assault, robbery, shooting, explosion, road accident, arson, vandalism
Contextual/social inference "Is what I am watching unwanted, coercive or distressing?" The whole video plus world knowledge about human intent and consent. Harassment, intimidation, stalking, bullying

This split has hard consequences. An object detector, no matter how accurate, cannot ever report that two people are fighting when no weapon is present — it has no access to motion, and each frame is scored in isolation. Conversely, an action classifier trained on 16-frame clips cannot report the pixel coordinates of a knife. And neither can distinguish an affectionate hug from a coercive grab, because that distinction lives in intent, persistence and the other person's reaction — semantics that only a model with broad world knowledge can access.

Harassment is a special case There is no off-the-shelf harassment classifier, and the project deliberately did not attempt to train one. Harassment is defined by intent, consent and persistence rather than by any visual signature; the UCF-Crime label set has no harassment class at all (Abuse and Assault are the nearest proxies and are poor ones). Current research addresses this with vision-language models and prompting, which is the route taken here — the Gemini path (§5.7) is the only backend that reports harassment, and its prompt explicitly instructs the model to judge from behaviour and to lower confidence or abstain when intent is ambiguous.

Project objectives

  1. Cover all six target detections by routing each to a model class capable of detecting it, rather than forcing one model to cover all.
  2. Never block the browser on a vision model — analysis must be asynchronous with live progress.
  3. Persist every result in a properly normalized relational schema, with no derived data stored and no JSON blobs.
  4. Make every reported incident evidenced: a timestamp range, a confidence, a still, a cut clip and a plain-language explanation.
  5. Let a non-technical operator interrogate a finished analysis in natural language, with citations.
  6. Degrade gracefully — a missing API key, an exhausted quota or a downed cache must never fail the whole run.

3.2 Request lifecycle

The defining property of the architecture is that the HTTP request and the model inference are completely decoupled. A POST to /detection/jobs does five things and returns: it validates the upload, computes a SHA-256 checksum (a duplicate upload becomes a lookup rather than a second analysis run), streams the bytes into MinIO, inserts a videos row and an analysis_jobs row, and pushes a job onto the Redis-backed ARQ queue. It responds 202 Accepted with a public job UUID in roughly one second, before any model has been touched.

The browser immediately opens GET /detection/jobs/{id}/events, a Server-Sent Events stream. Everything after this point arrives as events. The older synchronous endpoints (/detection/video, /detection/video/llm, and so on) remain functional for direct API consumers and now write into the same normalized tables, but the interactive path is entirely asynchronous.

This is deliberate — the cache must never be a single point of failure.

5. AI Models — Which, and Why

This is the core of the project. Six model families are integrated behind seven selectable strategies. This section states what each model is, precisely why it was chosen, what it cannot do, and how the choices compose.

5.1 The selection framework

Every model in the system was selected against four criteria, applied in order:

  1. Does its input representation match the question? A per-frame detector cannot answer a temporal question; a 16-frame clip classifier cannot answer a spatial one. This criterion alone eliminates most candidates for any given target.
  2. Is a suitable pre-trained checkpoint available? The project has no annotated dataset of its own and no training budget. Every model must be either pre-trained on a matching public dataset, zero-shot, or accessible as an API.
  3. What is the cost of being wrong? In a security context a false negative is far more expensive than a false positive, which argues for cascading multiple detectors rather than trusting one.
  4. Can the system function without it? Cloud models carry quota and connectivity risk. Every cloud dependency must have a local fallback, and every local model must be optional.

5.3 YOLOv8n — fine-tuned weapon detector

services/yolo_detection.py

What it is

A YOLOv8-nano single-stage object detector, fine-tuned on a weapon dataset to four fixed classes (Gun, Knife, Grenade, Explosive). The weights are downloaded from the Hugging Face Hub on first use and cached; a local .pt file can be substituted via YOLO_MODEL_PATH so that custom-trained weights drop in without a code change.

Why it was chosen

  • Precision on the exact classes that matter. A model fine-tuned on real firearms and blades substantially outperforms a general-purpose or zero-shot detector on those specific classes — which is the whole point of the weapon path.
  • Speed. The nano variant is the smallest YOLOv8 configuration. Sampling 24 frames across a video and running detection on each completes in seconds, which is what makes it a viable interactive default.
  • Localisation, not just classification. It returns [x1,y1,x2,y2] boxes, which the pipeline stores as four separate numeric columns and uses to draw annotated frames and boxed clips. No classifier can produce this.
  • Single-stage. One forward pass per frame, unlike two-stage detectors (Faster R-CNN) that propose regions and then classify them — roughly an order of magnitude slower for no benefit at this object size.

What it cannot do

It scores each frame independently. It has no concept of motion, so it cannot detect a fight, a robbery or an accident. It is also closed-vocabulary: anything outside its four trained classes is invisible to it. Both limitations are the reason the other models exist.

5.4 OWLv2 — zero-shot open-vocabulary detector

services/video_detection.py, services/explain.py

What it is

Google's OWLv2 (Open-World Localization v2), a vision transformer that performs open-vocabulary object detection: it takes text queries alongside the image and localises whatever those queries describe, with no training required for new classes. The system ships sixteen default queries — "a gun", "a rifle", "a machete", "a baseball bat", "a person holding a weapon", "blood", "a masked person" and others — and the API accepts arbitrary query lists at request time.

Why it was chosen

  • It removes the retraining bottleneck. YOLO knows four classes forever. Adding "a crowbar" to OWLv2 costs one string in a request. For a project with no annotation budget this is decisive.
  • It has a second, less obvious job. OWLv2 powers the explanation engine (services/explain.py). When the action model reports "Road Accident", OWLv2 is run over the clip with a vehicle/weapon/person query set, and the resulting object counts are composed into a sentence: "A road accident involving a car and a motorcycle, with people present." This turns a bare class label into something an operator can act on — and it does so locally, with no API call.
  • It cross-checks YOLO. Two independent detectors disagreeing on a weapon is itself useful signal.

What it cannot do, and how that is mitigated

Zero-shot generality costs precision: OWLv2 hallucinates low-confidence false positives, typically reporting a "truck" in a motorbike collision. The explanation engine handles this with a relative dominance filter rather than a fixed threshold — an object must appear in at least three sampled frames and reach at least half the count of the most-seen object to be mentioned. Genuine objects appear consistently across frames; hallucinations do not, so they fall away without needing a tuned absolute cutoff.

5.5 VideoMAE / UCF-Crime — action recognition

services/action_detection.py

What it is

VideoMAE-Large fine-tuned on the UCF-Crime dataset — 128 hours of real surveillance footage across thirteen anomaly classes. VideoMAE (Video Masked Autoencoder) is a video vision transformer pre-trained by reconstructing heavily masked spatio-temporal patches, which makes it unusually data-efficient for video classification. The checkpoint consumes fixed 16-frame clips.

Why it was chosen

  • It is the only model class that can answer the temporal question. Fighting, robbery and assault have no reliable single-frame signature. They are defined by how the scene changes. A transformer with temporal attention over a 16-frame stack sees that; a per-frame detector structurally cannot.
  • UCF-Crime is the closest public dataset to the project's target list. Its classes map almost one-to-one onto the requirements: Fighting, Assault, Abuse, Robbery, Shooting, Explosion, RoadAccidents, Arson, Vandalism, Burglary, Shoplifting, Stealing, Arrest. Alternatives were narrower — RWF-2000 and Real-Life-Violence-Situations are binary violence datasets; Hockey Fight is a single domain.
  • Real surveillance footage. UCF-Crime is untrimmed CCTV, so the domain gap to the project's actual input is small — a serious advantage over models trained on curated action clips such as Kinetics.
  • It is checkpoint-agnostic. Labels are read from model.config.id2label rather than hard-coded, so swapping in any Hugging Face video-classification checkpoint via ACTION_MODEL_ID requires no code change.

How it is run

A sliding window of 3 seconds with a 2-second stride is passed across the video. The overlap is deliberate: a non-overlapping window would miss an event that straddles a boundary. Each window is classified; windows whose top class is a "normal" class or whose confidence falls below threshold are discarded. Surviving windows of the same label that touch or overlap are merged into a single segment, so a ten-second fight is reported as one incident rather than five.

Two calibration decisions taken from observed behaviour Merged segments retain a peak. A merged span can cover an entire clip, making its midpoint meaningless. The merge therefore records peak_second — the midpoint of the highest-scoring constituent window — because that is the moment the model was most certain, and therefore the frame worth extracting and showing.

Confusable classes are presented honestly. On clean or out-of-distribution footage the model routinely confuses Abuse, Assault and Fighting with each other while still correctly identifying that physical violence is occurring. Rather than display a confidently wrong sub-label, all three are surfaced as "Fighting / Assault". Classes the model is reliable on — Shooting, Explosion, Road Accident — keep their proper names. This is a UI-honesty decision: report the granularity the model actually supports, not the granularity its label set advertises.

5.6 VideoMAE / violence — binary fight classifier

services/violence_detection.py

What it is and why a second video model exists

A VideoMAE-Base checkpoint fine-tuned on violence/non-violence datasets — a purely binary classifier over the same sliding-window scheme.

Adding a second video model may look redundant, but it addresses a measured weakness. The thirteen-way UCF-Crime classifier must distribute probability mass across all thirteen classes, and on ordinary footage it over-predicts weak "Fighting/Assault" at around 0.65 confidence, while genuine incidents score 0.95 and above. A binary classifier faces a far easier decision boundary and is consequently much more reliable on the single most common category — fights and assault.

The system exploits this directly in the auto cascade: the thirteen-way model is held to a deliberately high bar of 0.85, and borderline fights are handed to the binary classifier instead. Each model is used in the regime where it is strong, rather than being forced to be right everywhere.

5.7 Gemini 2.0 Flash — vision-language reasoning

services/llm_detection.py

What it is

Google's Gemini 2.0 Flash, a multimodal model that accepts native video input. The integration uses the REST API directly through httpx: the video is uploaded via the resumable Files API (which supports files far larger than inline-payload limits), polled until it reaches ACTIVE state, and then analysed with a structured prompt.

Why it was chosen — three reasons, in order of importance

  1. It is the only path to harassment detection. This is the decisive argument. No trainable classifier exists for harassment because it is not a visual pattern — it is an inference about intent, consent and persistence. The prompt directs the model to look for "one person's unwanted persistence and the other's discomfort or retreat", and instructs it to lower confidence or abstain when intent is ambiguous. A vision-language model with broad world knowledge is currently the only mechanism that can make this judgement at all.
  2. It produces explanations, not just labels. Every reported segment carries a natural-language description alongside its timestamps and confidence. The classifiers output a class index; Gemini outputs something an operator can read and act on.
  3. It covers all five categories in a single pass — violence, theft, harassment, accident and other hazards — where the local models each cover a slice.

How output reliability is enforced

The request sets response_mime_type: application/json together with an explicit OpenAPI-subset response_schema. The model is constrained to emit conforming JSON — violence_detected, summary, and a segments array whose category field is restricted by enum to the five valid values. This removes an entire class of failure: there is no prose to parse, no regex extraction, and no possibility of an unrecognised category reaching the database.

Accepted trade-offs Gemini is the only cloud dependency in the detection path. It requires an API key, incurs per-call cost, is subject to quota exhaustion, and means video content leaves the machine — a genuine privacy consideration for surveillance footage. Every one of these is mitigated by design: the auto cascade treats a Gemini failure (missing key, exhausted quota, network error) as a skip rather than an error and continues to the local models, and the qwen backend below provides an offline equivalent. The system is fully functional with no API key at all — it simply loses harassment detection.

5.8 Qwen2.5-VL-7B — offline vision-language fallback

services/qwen_detection.py, qwen_infer.py

Alibaba's Qwen2.5-VL-7B-Instruct is an open-weights vision-language model with native video understanding. It exists in this system for one reason: to provide Gemini's capability — natural-language incident description with timestamps — without sending footage off the machine. For deployments where surveillance video cannot leave the premises, this is the difference between the platform being usable and not.

The subprocess isolation decision

Qwen2.5-VL requires a bleeding-edge transformers build plus qwen-vl-utils and decord, whose version constraints conflict with the backend's pinned FastAPI/Pydantic/Prisma stack. Rather than compromise the API's dependency tree, the model lives in a completely separate virtual environment (qwen_env) and is invoked as a subprocess. The child process prints its structured result on a single line prefixed with a sentinel (__QWEN_RESULT__), which the parent locates in stdout and parses as JSON.

This is an unglamorous but genuinely correct engineering choice: it buys hard dependency isolation and crash containment (a CUDA out-of-memory error kills the child, not the API) at the cost of process-spawn overhead — negligible against a multi-minute inference. The honest downside is speed: 7-billion-parameter inference on CPU is slow enough that the timeout is set to 1800 seconds.

5.9 Qwen2.5-7B — agent orchestration and text-to-SQL

services/qwen_chat.py, services/chat_agent.py, services/db_agent.py

A separate, text-only Qwen2.5-7B model drives the conversational layer. It is reached over any OpenAI-compatible endpoint — the default targets a local Ollama install, but vLLM, llama.cpp or DashScope work unchanged.

Why a local model for the agent, and why Qwen

  • Volume. The agent is called on every conversational turn and may make several tool round-trips per message. Routing that to a paid API would dominate the system's running cost; a local model makes conversation free.
  • Reliable function calling. Qwen2.5 was trained for tool use and emits well-formed tool calls, which is the single hard requirement for an orchestrator.
  • Competent SQL generation. The database insights agent needs a model that writes correct PostgreSQL against a described schema — a documented Qwen2.5 strength.

Protocol robustness

Tool calling is normalised across two protocols so the agent works regardless of what the serving stack supports: the native OpenAI tools / tool_calls fields, and Qwen's own text protocol in which the model emits <tool_call>{...}</tool_call> inside the reply body, parsed out with a regular expression. A third fallback catches fenced ```json blocks. If the endpoint is unreachable entirely and QWEN_CHAT_ALLOW_LOCAL_FALLBACK is enabled, the system falls back to running Qwen in qwen_env as a subprocess — fully offline, slow, and text-protocol only.

5.10 The auto cascade and its ordering

services/detection_runner.py

auto is the recommended strategy for a user who does not know what to look for. It runs three backends in a fixed order and stops at the first positive detection. 

  auto
   │
   ├─ 1. GEMINI 2.0 FLASH ───────── incident found? ──► RETURN
   │     best coverage; only path to harassment
   │     skipped silently on missing key / quota / network error
   │
   ├─ 2. VIOLENCE CLASSIFIER ────── incident found? ──► RETURN
   │     binary, high accuracy on fights and assault
   │
   ├─ 3. ACTION MODEL (UCF-Crime) ─ incident found? ──► RETURN
   │     threshold raised to 0.85 — covers robbery, arson,
   │     road accidents, shooting, the long tail
   │
   └─ nothing found ──► return the first "clear" verdict obtained
Figure 5.1 — The auto cascade. Every stage is individually optional; a failure is a skip, never an error.

Why this order and not another

RankBackendJustification for its position
1stGemini 2.0 Flash Widest category coverage and the only harassment detector, so putting it anywhere else means harassment is missed whenever an earlier stage fires. It is also fast in wall-clock terms and produces the richest output. Its only weakness — external availability — is precisely what the fallbacks exist for.
2ndViolence classifier Fights and assault are the most common real-world category, and this binary model is the most accurate available on exactly that category. It therefore gets the first look among the local models.
3rdAction model @ 0.85 Broadest local class coverage (robbery, arson, road accidents, shooting) but the noisiest, so it runs last and only accepts high-confidence predictions. It exists to catch what the two above structurally cannot see.

The cascade also maintains a "clear" result: if a stage runs successfully and finds nothing, that verdict is retained. If no stage detects anything, the retained clear verdict is returned rather than a synthetic empty one, so the report shows which model actually cleared the video.

Finally, model_code_from_result() inspects the winning result and records the model that actually produced it on the scans row, while the analysis_jobs row keeps the model that was requested. For an auto run these genuinely differ, which is why the schema stores both and neither is redundant (see §8).

5.11 Alternatives considered and rejected

Table 5.2 — Rejected approaches and the reasoning
AlternativeWhy it was not used
Training a custom action model from scratch on UCF-Crime + RWF-2000 Weeks of GPU time, severe class imbalance on the rare and most important classes (killing, harassment), and an almost certain accuracy loss against a published fine-tuned checkpoint. The engineering effort was better spent on the pipeline, the cascade and the evidence layer — which is where this system's actual contribution lies.
A single end-to-end multi-task model Would need to simultaneously produce pixel boxes, temporal segments and contextual judgements. No such model exists off the shelf, and building one would require exactly the annotated dataset the project does not have.
3D CNNs — I3D, SlowFast, C3D The prior generation of video action recognition. VideoMAE's masked-autoencoder pre-training gives better accuracy with less fine-tuning data, and it integrates directly through transformers with no bespoke loading code.
Faster R-CNN / two-stage detectors Roughly an order of magnitude slower than single-stage YOLO for no meaningful accuracy gain at the object sizes involved. Interactive latency was a hard requirement.
CLIP-based frame classification Gives a whole-frame similarity score with no localisation and no temporal modelling — strictly worse than OWLv2 for the object task and useless for the action task.
GPT-4V / Claude for video At the time of building, Gemini's native video input with the Files API and constrained JSON output was the cleanest fit. The abstraction in detection_runner.py means adding another vision-language backend is a single new function plus a registry entry.
Pose estimation (OpenPose / MediaPipe) with a fight heuristic Brittle in crowds, in poor lighting and under occlusion — all defining characteristics of real CCTV footage. It also requires hand-written rules for what constitutes a fight, which is precisely what a learned model does better.

5.12 Inference post-processing

Raw model output is not shown to the user. Four post-processing stages sit between the model and the report.

Sliding-window merge

Overlapping windows of the same label that touch are merged into one segment, and the merged span keeps the peak confidence and the peak timestamp. A ten-second fight becomes one incident, not five.

Category mapping

Each model's native labels are mapped onto the five shared categories, so a UCF-Crime Burglary, a Gemini theft and a YOLO Gun all land in a schema the frontend can group and colour consistently.

Object-grounded explanation

OWLv2 names the objects involved and composes a sentence — "A road accident involving a car and a motorcycle, with people present" — with the relative-dominance filter of §5.4 suppressing hallucinated objects.

Evidence extraction

Each incident yields a cut video clip, a bounding-boxed version of that clip, and a still frame from its midpoint, all stored in MinIO and linked to the segment row.

Frame-level captioning

Every sampled frame receives a caption, chosen from three sources in order of specificity: the incident whose time range contains the frame; otherwise the objects the detector boxed on that frame; otherwise an explicit "Clear — nothing flagged at 0:14". Object captions are produced by a single SQL statement that assigns every detection box to the frame nearest it in time (an OWLv2 pass can emit several hundred boxes — one round-trip each would cost more than the detection did) and a second statement that aggregates them into readable text such as "gun ×3 (91%)".

6. Asynchronous Analysis Pipeline

worker.py — ARQ task analyze_video

6.1 Stage-by-stage walkthrough

Table 6.1 — Pipeline stages with their progress ranges
ProgressStageWhat happens
0–5 %downloading Fetch the video from MinIO to a temporary local file (models need a real path), probe duration, resolution and frame rate, write them back onto the videos row.
5–30 %extracting_frames Sample N frames evenly, upload each JPEG to MinIO, insert an images row, and emit a frame.ready event carrying a ready-to-render presigned URL. This happens before any model loads.
30–70 %detecting Run the selected backend, or the auto cascade. Inference is dispatched with asyncio.to_thread so the worker's event loop stays responsive and can keep publishing progress while a model runs.

6.2 Why frames are extracted first

Ordering the pipeline this way is a perceived-performance decision, and it is measurable. Decoding a dozen frames takes under a second; a vision model takes anywhere from five seconds to several minutes. By sampling, uploading and announcing frames before the model is loaded, the browser paints real imagery from the user's own video almost immediately, instead of showing a spinner for the entire run. 

 0.0s  job.queued

 1.0s  frame.ready     7%    ← first real image on screen
 2.1s  frame.ready    30%    ← all 12 frames on screen

6.3 Failure handling and retries

  • Every relational field is read once, up front. Prisma's update() returns a record with relations unset, so anything reached through job.video after the first status write would silently be None — a subtle bug the code guards against explicitly.
  • Optional steps are individually wrapped: a failed clip extraction, a failed box annotation or a failed explanation logs and continues. None of them can fail the analysis.
  • A genuine failure sets status = FAILED, records the error message on the job row, invalidates the cache and emits job.failed before re-raising for ARQ.
  • The temporary video file is removed in a finally block regardless of outcome.
  • Worker limits: max_jobs = 2 (two concurrent jobs is the ceiling for memory-hungry vision models on a single GPU), a 1800-second job timeout, and two attempts per job.
  • POST /detection/jobs/{id}/retry re-queues a failed job against the already-stored video, so the user does not re-upload.

7. Real-Time Event System

7.1 The event log as single source of truth

Every meaningful occurrence during a job becomes one append-only row in job_events. That row — not the worker's local state — is the single source of truth, and it feeds both delivery channels. 

  worker ──► job_events (Postgres, append-only, numbered per job)
                   │
      ┌────────────┴─────────────┐
      ▼                          ▼
  Redis pub/sub              webhook dispatcher
      │                          │
  SSE stream                 signed HTTP POST
      ▼                          ▼
   browser                  subscriber's server
Figure 7.1 — One log, two transports. Payloads are byte-identical; only the delivery mechanism differs.

A browser cannot receive an inbound HTTP callback, which is the only reason two transports exist. Because both are built from the same row by the same build_payload() function, a webhook consumer and the user interface can never disagree about what happened.

Seven event types are defined: job.queued, job.started, job.progress, frame.ready, segment.ready, job.completed, job.failed. The last two are terminal — the SSE stream closes after either.

7.2 Server-Sent Events

Events are numbered with a monotonic per-job sequence, sent as the SSE id: field. When a connection drops, the browser automatically resends the last identifier as Last-Event-ID, and the server replays only what came after it. Two details make this correct rather than merely plausible:

  • The Redis subscription is opened before history is replayed from Postgres. Opening it afterwards would leave a window in which an event published between the two is lost forever.
  • UNIQUE (job_id, sequence) at the database level guarantees the numbering has no gaps and no duplicates, which is what makes the replay exact.

frame.ready carries the image record complete with a presigned URL, so the browser renders the thumbnail directly from the event with no follow-up request. segment.ready carries the incident along with its cut clip and boxed clip.

7.3 Signed webhooks

Users register endpoint URLs and subscribe to a subset of event types. The signing secret is returned exactly once, at creation. Each delivery carries four headers: 

X-Vision-Event:      frame.ready
X-Vision-Delivery:   1421
X-Vision-Attempt:    1
X-Vision-Signature:  t=1786...,v1=9f2c...

The signature is HMAC-SHA256(secret, "{timestamp}.{raw_body}"). Because the timestamp is inside the signed string, a captured request cannot be replayed later — a receiver rejecting timestamps older than its tolerance window is cryptographically safe. Verification must run over the raw body; re-serialising the JSON changes the bytes and invalidates the signature. Failed deliveries retry with exponential backoff (2 s, 8 s, 30 s, 120 s) up to a configurable attempt limit, and each attempt is recorded as a webhook_deliveries row with its status code, duration and error. The body itself is never stored — it is rebuilt from the referenced job_event, so there is no second copy to drift out of sync.

8. Database Design (Third Normal Form)

prisma/schema.prisma · full justification in docs/NORMALIZATION.md

8.1 The original schema and its defects

The first implementation stored an entire analysis in one row of a detection_scans table, with a labels TEXT[] column and a result JSONB blob. It worked, and it was wrong in four specific, diagnosable ways.

Table 8.1 — Normalization defects in the original design
DefectWhereBreaksConsequence
Repeating group in a columnlabels TEXT[]1NF "Every scan tagged Gun" requires unnest() or an array scan; no index helps, and a mistyped label can never be corrected in one place.
Nested relations in a blobresult JSONB1NF Segments and object boxes are entities with their own attributes. Buried in JSON they cannot be constrained, indexed, joined or aggregated.
Derived data storedresult->'label_counts'3NF It is a COUNT(*) GROUP BY label over detections in the same blob. Two copies of one fact inevitably drift apart.
Free-text foreign keysmodel TEXT3NF Renaming a model, or recording that it runs locally, means an UPDATE across every historical row — a textbook update anomaly.

8.2 The normalized design

users
  └── videos                        (user_id)
        ├── analysis_jobs           (video_id, model_id) ── job_queries
        │     └── scans             (job_id, model_id)
        │           ├── segments    (scan_id, label_id, category_id)
        │           ├── detections  (scan_id, label_id, image_id)
        │           ├── scan_labels (scan_id, label_id)              M:N
        │           └── chat_sessions └── chat_messages └── chat_citations
        └── images                  (video_id, segment_id)

detection_models · incident_categories · labels                lookup tables
job_events → webhook_deliveries → webhook_endpoints ── webhook_subscriptions
Figure 8.1 — Entity relationships. 27 tables, no array columns and no JSON columns in the operational schema.

Key design decisions

  • Ownership is stored exactly once and reached by traversal. analysis_jobs has deliberately no user_id — the owner is job → video → user. Copying it onto the job would make user_id transitively dependent on video_id, which is precisely the 3NF violation the schema exists to avoid. The same reasoning removes user_id from scans, segments and frame images.
  • Lookup tables for open-ended sets. detection_models, incident_categories and labels store each name once and are referenced by id. Labels arrive from models as free text ("Fighting", "a gun") and are interned on write, which is what allows scan_labels to be a proper M:N join.
  • Requested versus produced model. analysis_jobs.model_id is what the user asked for; scans.model_id is what actually generated the result. For an auto run these genuinely differ, so neither is redundant.
  • Lists become rows. OWLv2's free-text query list is job_queries, ordered by ordinal. A webhook endpoint's subscribed events are webhook_subscriptions, not an events TEXT[] column.
  • Coordinates are atomic. box_xyxy: [x1,y1,x2,y2] became four numeric columns — a coordinate pair is not an atomic value.
  • Derived aggregates are computed, never stored. label_counts is gone; it is a GROUP BY over detections, computed on read.
  • A database constraint enforces single-source ownership on the shared images table: CHECK ((user_id IS NULL) <> (video_id IS NULL)). An UPLOAD has a user and no video; a FRAME has a video (whose owner is the user) and no user. The two can therefore never disagree. Prisma cannot express a CHECK, so the migration script applies it.
  • Deduplication by content. UNIQUE (user_id, checksum_sha256) on videos makes re-uploading the same bytes a lookup rather than a second copy and a second analysis run.

8.3 Documented exceptions

Two deliberate choices are recorded so they are not mistaken for oversights.

  1. Enums live in the type system, not in lookup tables. JobStatus, ImageKind, ChatRole and DeliveryStatus are closed sets that carry no attributes beyond a name. A lookup table would add a join for zero benefit. Open-ended sets that do carry attributes and change at runtime — labels, models, categories — get real tables.
  2. scans.summary is not derivable. It might look like a function of the segments, but the vision models write a natural-language summary that no query over segments could reconstruct. It is a genuine attribute of the scan.

A migration script, migrate_normalize.py, backfills the legacy table into the new structure, fanning each old row out into videos + analysis_jobs + scans + segments / detections + scan_labels. On the development database it moved 30 legacy rows into 24 segments, 803 object detections, 16 interned labels and 74 scan-label links. It supports --dry-run and is safe to re-run.

9. Conversational AI Layer

Three distinct agents serve three distinct purposes. Keeping them separate — with different models, different prompts and different privileges — is what makes each one reliable.

9.1 Agent A — tool-using orchestrator

services/chat_agent.py + services/agent_tools.py · driven by Qwen2.5-7B · route /chat

"SentinelAI" is the general-purpose assistant. A conversation owns its own uploaded video and may produce several scans. Qwen decides when to reach for a tool; six are exposed:

ToolWhat it does
analyze_videoRuns a chosen detection backend over the session's video and persists the scan. The tool schema describes each backend in prose so the model picks sensibly; YOLO is the default, auto for thorough behavioural coverage.
query_detection_databaseHands a plain-English question to Agent C (§9.3).
control_video_playbackDrives the browser's player — play, pause, replay, seek, play_segment. No server-side effect; the executor validates and the frontend carries it out.
show_frame_atCaptures the exact still at one second and displays it inline in the conversation.
list_recent_scans / get_scan_reportRead stored history and full reports.

The system prompt enforces operator-appropriate behaviour: lead with the verdict then the evidence; show rather than describe (any request to "play that again" is a playback call, not a sentence about one); report when and where together using the frame location the tool returned ("the gun appears at 00:02, centre of frame") and never guess a location the tool did not supply; never invent a detection, timestamp or count. Tool rounds are capped at four per user message to prevent loops, and history is replayed as plain turns with session facts injected into the system prompt — keeping replays small and preventing tool-id desynchronisation.

9.2 Agent B — grounded per-scan analyst

services/scan_chat.py · Gemini 2.0 Flash · route /detection/scans/{id}/chat

Every finished scan gets its own read-only conversation. This agent answers questions about that one video and nothing else. Grounding is enforced in three independent ways:

  1. Instruction. The system prompt forbids claims unsupported by the supplied evidence and requires the phrase "the analysis does not show that" when an answer is not in the data.
  2. Structured citation. The model returns JSON naming the segment ordinals and frame sequences it used. These are written to chat_citations and rendered beneath the reply, so any claim traces back to evidence.
  3. Actual images. Frames are attached to the prompt as real image data, so a question about the scene — "what is the person on the left carrying?" — is answered by looking, not by inferring from a caption.

Three backends are tried in order: Gemini (multimodal), the local Qwen server (text-only), then a plain readout of the stored analysis. The response carries a source field, and the interface visibly labels a fallback reply rather than passing it off as reasoning — an honesty property that matters when the answer quality differs by an order of magnitude between tiers.

9.3 Agent C — text-to-SQL insights

services/db_agent.py · Qwen2.5-7B

Questions about counts, trends and comparisons across past videos are delegated to a database analyst agent. It asks Qwen to write a read-only SELECT, validates it, executes it, and asks Qwen to turn the rows into a short insight.

The containment model — four independent layers 1. The model never sees real tables. The generated query runs on top of a fixed CTE prelude exposing exactly three relations — scans, frames, events — every branch of which is filtered by user_id = $1. Cross-tenant access is structurally impossible, not merely forbidden.
2. Relation allowlist. Every FROM and JOIN target is extracted and checked against the permitted set; anything else is rejected before execution.
3. Keyword denylist. A regular expression rejects every mutating or escalating construct — INSERT, UPDATE, DELETE, DROP, GRANT, COPY, pg_read_file, pg_sleep, information_schema, pg_catalog — and also names the sensitive tables (users, images, the chat tables) explicitly. SQL comments are stripped first so they cannot be used to smuggle a keyword past the check.
4. Row cap. Every query is limited to 200 rows, with 40 fed back to the model for summarisation.

12. Security Model

12.1 Authentication and authorisation

  • Password storage. bcrypt with per-password salt generation. Inputs are truncated to bcrypt's 72-byte limit identically on the hash and verify paths — an asymmetry here is a classic silent authentication bug.
  • Tokens. HS256 JWTs with a configurable expiry, issued through the OAuth2 password flow and validated by a FastAPI dependency that decodes the token and loads the user on every protected request.
  • Email verification. Signup issues a time-limited OTP; login is refused until the account is verified. The same mechanism backs password reset.
  • Ownership checks. Because ownership is reached by traversal rather than duplicated, every access check follows the same path — scan → job → video → user — and there is no second copy of user_id that could be checked inconsistently.
  • CORS. Allowed origins are an explicit configured list, not a wildcard.

12.2 Upload validation and storage

  • File type, MIME type and size are validated before any byte reaches storage; the video path enforces a 200 MB ceiling.
  • Stored filenames are generated, never taken from user input — closing the path-traversal and collision classes at once.
  • Binary data lives only in MinIO. The browser receives presigned URLs with a bounded lifetime (default one hour), so object keys are never publicly enumerable.
  • Webhook secrets are shown exactly once, at endpoint creation.

12.3 SQL agent containment

The text-to-SQL agent is the highest-risk surface in the system — a language model writing queries against a live database. Its four-layer containment is described in §9.3. The essential property is that the innermost layer is structural: the model can only reference three CTEs, each already filtered to the calling user, so even a query that defeats every validator cannot read another user's data.

Known gaps, stated plainly There is no rate limiting on authentication endpoints, no refresh-token rotation (tokens simply expire), and no audit log of administrative actions. Admin identity is determined by matching a configured email address rather than by a role column. These are appropriate for the current scope and are listed in §16 as the first items for production hardening.

13. Performance & Caching

13.1 Cache design

Dashboard statistics, scan history and finished reports are cached in Redis under a per-user namespace: 

v1:{user_generation}:{namespace}:{user_id}:{suffix}

Invalidation bumps the user's generation counter with a single INCR, which logically expires every key belonging to that user without scanning the keyspace — an O(1) operation regardless of how many entries exist. The worker performs this bump when a job finishes.

A subtle correctness constraint Cached report payloads embed presigned URLs. Their cache TTL (120 s) is therefore deliberately set far below the signature lifetime (3600 s). If the ordering were reversed, a cache hit could hand the browser a URL that had already expired — a bug that would be intermittent, environment-dependent and extremely unpleasant to diagnose.

13.2 Other performance measures

  • Models are loaded once and cached in module globals. The first request pays the load cost; every subsequent request reuses the resident model.
  • Blocking inference is offloaded with asyncio.to_thread, keeping the worker's event loop free to publish progress events while a model runs.
  • Bulk SQL over per-row round-trips. Linking several hundred detection boxes to their nearest frames is two statements, not several hundred — the round-trips would have cost more than the detection itself.
  • Reference-table ids are memoised in-process. Lookup rows never change at runtime, so caching their ids removes a join from every write in the worker's hot loop.
  • Content-addressed deduplication. A SHA-256 checksum means re-uploading the same video is a lookup, not a second full analysis.
  • Database indexes on every foreign key and on the query patterns that matter: (user_id, uploaded_at), (status, queued_at), (scan_id, start_time), (video_id, sequence).
  • GPU acceleration is automatic when a CUDA build of torch is present, with a transparent CPU fallback.

14.3 Operational notes

  • Two Python environments exist and must not be confused: env is the backend, qwen_env holds only the local Qwen vision model with its conflicting dependencies.

  • Postgres is on host port 5434 because 5432 and 5433 are held by native Windows PostgreSQL services on the development machine.
  • Data persists in Docker named volumes. docker compose down keeps it; down -v destroys it.
  • The API must be started with --reload during development, or newly added routes return 404 against a stale process.

16. Limitations & Future Work

16.1 Honest limitations

LimitationDetail and current mitigation
Action-model class confusion The UCF-Crime classifier reliably distinguishes violence from normality but confuses Abuse, Assault and Fighting with one another. Mitigated by presenting all three as "Fighting / Assault" rather than displaying a confidently wrong sub-label.
Harassment depends on a cloud model Without a Gemini key, harassment detection is unavailable. There is no local substitute because no off-the-shelf harassment classifier exists. Qwen2.5-VL is the nearest offline option and is markedly slower.
No quantitative evaluation on a held-out set The project integrates published checkpoints and validates behaviour on sample clips, but does not report precision/recall against an annotated test set of its own. This is the single largest gap between the current state and a research-grade claim.
Fixed sampling density The object detectors sample a fixed number of frames regardless of video length, so a very brief weapon appearance in a long video can fall between samples.
Local VLM latency Qwen2.5-VL on CPU takes minutes; the timeout is set to 1800 s. Practical only as an offline fallback, not as an interactive default.
Worker concurrency ceiling max_jobs = 2 is set by single-GPU memory. Scaling requires moving the models to a dedicated inference host.
Privacy of cloud analysis Choosing the Gemini backend sends footage to an external service — a genuine consideration for surveillance material, and the reason the offline path exists.

16.2 Future work, in priority order

  1. Quantitative evaluation. Assemble an annotated held-out set and report per-class precision, recall, F1 and a confusion matrix for every backend; use the results to set per-class confidence thresholds empirically rather than by observation.
  2. Fine-tune the action model on the project's own label set, combining UCF-Crime with RWF-2000 and Real-Life-Violence-Situations, with explicit handling of class imbalance on the rare categories. This directly targets the Abuse/Assault/Fighting confusion.
  3. Result fusion instead of first-hit cascade. Run detectors in parallel and combine their outputs with confidence weighting, so an object detection and an action detection at the same timestamp reinforce one another rather than one short-circuiting the other.
  4. Production security hardening. Rate limiting on auth endpoints, refresh-token rotation, a proper role column instead of email matching, and an administrative audit log.
  5. Adaptive frame sampling driven by motion energy, so activity-dense regions are sampled more densely than static ones.
  6. Live stream ingestion — RTSP input with rolling-window analysis, which the sliding-window design already accommodates conceptually.
  7. Horizontal scaling — multiple workers behind a dedicated GPU inference service, which the ARQ architecture supports without redesign.
  8. Alerting integrations — email, SMS or push notification on high-severity detections, layered on the existing webhook infrastructure.

Closing note The defining characteristic of this project is not any single model — every checkpoint it uses is publicly available. It is the recognition that violence detection decomposes into three incompatible machine-learning problems, and the system built around that recognition: a cascade that routes each question to a model capable of answering it, an asynchronous pipeline that keeps the interface responsive while heavy models run, a normalized schema that makes results queryable rather than merely storable, and a grounded conversational layer that cites its evidence instead of inventing it.
